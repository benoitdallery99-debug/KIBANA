# M5 — Industrialiser

Vous avez construit deux écrans dans un lab qui sera éteint. Ce module ne
parle plus d'enquête : il les rend transportables — vers une autre
plateforme, vers un autre Space, vers un dépôt de code où ils se relisent
en revue — et pose les seules alertes que la licence autorise.

## Deux formats d'export, et un seul se réimporte

![](capture:M5-C1)

| Format | Où il s'obtient | Ce qu'il porte |
|---|---|---|
| ndjson | « Objets enregistrés », bouton « Exporter » | l'objet entier, et ses références |
| JSON de l'API | menu « Exporter » d'un tableau de bord | ce que l'API sait relire |

Le ndjson sert à sauvegarder et à migrer : il est fidèle, il référence la
data view, et c'est le seul format que l'import accepte. Le JSON de l'API
sert à versionner : lisible en revue, rejouable par une commande, mais il
retire sans le dire les propriétés qu'il ne connaît pas.

Deux conséquences que l'on découvre trop tard. La première : depuis un
tableau de bord ouvert, « Exporter » ne donne plus de ndjson, et le volet
qui s'ouvre porte le badge « VERSION D'ÉVALUATION TECHNIQUE » alors même
que la documentation annonce la fonction comme stable. Le ndjson ne
s'obtient plus que par la page des objets enregistrés. La seconde : un
support de formation recyclé d'une version antérieure est faux sur ce
point précis.

## Un export ne remonte pas le temps

La règle tient en une phrase : un export se réimporte dans la même
version, dans une mineure plus récente de la même majeure, ou dans la
majeure suivante. Une majeure d'écart, pas deux.

| Depuis cette version, vers | Verdict |
|---|---|
| la même version | accepté |
| une mineure plus récente de la même majeure | accepté |
| la majeure suivante, quelle que soit sa mineure | accepté |
| une version antérieure | refusé |
| deux majeures plus loin | refusé |

Si la plateforme cible est en retard, c'est elle qu'il faut monter : le
fichier, lui, ne se retouche pas. Et l'on ne retire jamais d'un ndjson
édité à la main les champs qui disent à la cible comment le lire.

## L'identifiant fixe de la data view

Un tableau de bord construit dans l'interface ne contient pas le motif
d'index : il contient une **référence** vers la data view, par
identifiant. Sur la cible, cette référence doit retrouver un objet du même
identifiant, sinon l'écran arrive sans données.

Kibana attribue cet identifiant au hasard, sauf si vous le choisissez.
À la création d'une data view, « Afficher les paramètres avancés » ouvre
le champ « ID de vue de données personnalisé ». Le champ « Modèle
d'indexation », lui, reste propre à chaque plateforme : le lab vise ses
index, la cible vise ceux de production.

C'est tout le mécanisme du transport : **identifiant identique des deux
côtés, motif différent de chaque côté**, et un fichier d'export qu'on ne
retouche pas.

## L'API Dashboards

Elle est servie en licence Basic dans cette version, ce qui n'allait pas
de soi. Deux routes, et elles ne se valent pas :

| Route | Comportement | Usage |
|---|---|---|
| `PUT /api/dashboards/{id}` | crée ou remplace l'écran d'identifiant donné | le versionné |
| `POST /api/dashboards` | engendre un nouvel identifiant à chaque appel | le ponctuel |

Ce sont là les routes HTTP, telles qu'un script les appellera. **Depuis la
console de Kibana, préfixez-les de `kbn:`** — `PUT kbn:/api/dashboards/{id}` —,
faute de quoi la console envoie l'appel à Elasticsearch, qui répond « no handler
found for uri ». Et n'y ajoutez pas `/s/<space>` : un appel `kbn:` part déjà
dans le Space où la console est ouverte. Le préfixe de Space, lui, sert depuis
l'extérieur — avec `curl`, par exemple.

Un fichier du dépôt doit pouvoir être appliqué deux fois sans
conséquence : c'est PUT. Le même script lancé deux fois avec POST laisse
deux écrans derrière lui.

PUT remplace **intégralement**, et il n'existe pas de modification
partielle : un panneau absent du corps envoyé est supprimé. L'enchaînement
correct est donc toujours lire l'écran, modifier le corps entier, le
renvoyer.

**Ce que cette API refuse.** Une source de données qui désigne la data
view par son identifiant. Seul le motif d'index écrit en ligne dans le
panneau est accepté. Un écran défini en code n'a donc aucune référence :
il est autonome, mais son motif est inscrit dedans, et c'est lui qu'il
faudra changer pour la cible.

| Voie | Référence la data view | Ce qu'on adapte pour la cible |
|---|---|---|
| interface, puis export ndjson | oui, par identifiant fixe | rien dans le fichier |
| API Dashboards | non, motif en ligne | le motif, dans le fichier |

L'identifiant fixe garde donc tout son sens — pour la première voie. Les
deux ne se concurrencent pas : on versionne en code ce qui doit être relu,
on transporte en ndjson ce qui a été construit à l'écran.

Un provider Terraform existe pour aller plus loin ; il est en version
d'évaluation technique, et le kit ne l'enseigne pas.

## Importer ailleurs : ce que Kibana fait vraiment

Un tableau de bord est un objet partageable entre Spaces. Importer un
export dans un Space où le même identifiant existe déjà **n'écrase rien et
n'échoue pas** : Kibana crée une copie sous un nouvel identifiant, qu'il
renvoie dans `destinationId`. Ce comportement ne dépend pas de l'option
d'import choisie ; il se produit aussi quand la création de nouvelles
copies est désactivée.

Vous vous retrouvez donc avec deux écrans qui portent le même titre et qui
divergeront dès la première retouche. Pour mettre à jour un écran qui
existe déjà ailleurs, l'import n'est pas le bon geste : la seule voie
idempotente est de viser son identifiant dans le Space visé.

### Hors licence Basic

**La planification d'exports récurrents n'existe pas, CSV compris.** Le
téléchargement à la demande, oui ; le même export automatiquement chaque
lundi, non. Le piège est double : la documentation ne mentionne aucune
licence pour cette fonction, et c'est le code de la version qui la réserve
à un niveau supérieur. Vous ne le découvrirez donc qu'en essayant, souvent
après l'avoir promis. Promettez un lien vers un écran vivant, pas un envoi
automatique.

## Alerter avec ce que la licence donne

Trois types de règles couvrent l'essentiel du besoin SOC, et les trois
sont utilisables ici :

| Type de règle | Ce qu'il évalue |
|---|---|
| « Recherche Elasticsearch » | le nombre de documents que renvoie une requête |
| « Seuil de l'index » | une agrégation sur un champ, comparée à un seuil |
| « Seuil personnalisé » | un seuil sur une data view, avec filtres et groupement |

Une règle sans action ne fait rien de visible : il lui faut un connecteur.
Côté serveur, l'alerting exige aussi une clé de chiffrement des objets
enregistrés ; sans elle, les règles ne sont pas disponibles du tout. Enfin,
un système d'alerting de seconde génération existe en version d'évaluation
technique : ne le confondez pas avec les règles décrites ici.

### Hors licence Basic

**Deux connecteurs sur soixante-treize.** Relevé sur le lab, et non déduit
d'une page de documentation : seuls `.index` et `.server-log` sont
utilisables. Pas de courriel, pas de messagerie d'équipe, pas de webhook.
Ils figurent tous dans la liste, et sont refusés à l'usage. « Et ça
m'envoie un mail ? » est la première question de la salle : elle se traite
à la première réunion, pas à la mise en production.

Ce qui reste suffit plus souvent qu'on ne croit. Le connecteur d'index
écrit l'alerte dans un index dédié : vous posez une data view dessus, puis
un écran ou une session Discover, et la salle voit les alertes arriver là
où elle regarde déjà. Le connecteur de journal serveur écrit dans le
journal de Kibana : utile pour prouver qu'une règle s'est déclenchée,
inutile pour prévenir quelqu'un.

## Détecter un silence

C'est la règle que tout le monde croit avoir écrite, et que presque
personne n'a écrite.

Une source muette ne produit aucun document, donc aucun groupe.
Un seuil « moins de un événement » **groupé par source** ne
se déclenchera jamais pour elle : il n'y a pas de groupe à évaluer. La
règle reste verte pendant toute la panne, ce qui est pire que pas de règle
du tout.

Deux formulations tiennent :

1. **Une règle par source, sans groupement.** Sa requête ne vise qu'une
   source ; le compte renvoyé vaut zéro, et zéro est une valeur que la
   condition sait comparer. Coût : autant de règles que de sources, et
   une de plus à chaque nouvelle source.
2. **Le dernier événement vu par source, sur une fenêtre longue.** C'est
   le panneau de l'écran de santé de la collecte. Coût : il ne prévient
   personne tout seul, c'est un écran, pas une alerte.

Un SOC sérieux pose les deux : la règle réveille, l'écran explique.

## Rôles et Spaces

En licence Basic, le cloisonnement passe par le Space, et par rien
d'autre.

- Les privilèges se posent **par Space** : soit de base, en lecture ou en
  accès complet, soit fonctionnalité par fonctionnalité — le lab en sert
  cinquante-trois, toutes disponibles avec cette licence.
- Les **sous-privilèges** d'une fonctionnalité n'existent pas ici : on ne
  peut pas accorder le téléchargement CSV seul.
- La sécurité **au niveau du document et du champ** est hors licence :
  vous ne pouvez masquer ni certaines lignes ni certains champs à un rôle.

La conséquence est structurante, et elle se décide avant la première data
view : un périmètre égale un motif d'index, plus un Space, plus un rôle
qui n'ouvre que ce Space. Deux équipes qui ne doivent pas voir les mêmes
journaux ne partagent pas la data view — et aucune subtilité de rôle ne
rattrapera ce choix après coup.

## Ce que vous emportez de ce module

1. **Le format dépend de l'usage.** Le ndjson transporte, le JSON de
   l'API versionne. Ils ne contiennent pas la même chose, et aucun des
   deux ne remplace l'autre.
2. **Un identifiant se choisit, il ne se subit pas.** Celui de la data
   view se fixe à la création, une fois pour toutes, et c'est lui qui rend
   un export rejouable ailleurs.
3. **Une alerte qui ne peut pas se déclencher est pire que pas
   d'alerte.** Une détection de silence se vérifie en regardant une
   source se taire, jamais en relisant sa définition.

Le parcours s'arrête ici. Ce qu'il vous laisse n'est pas une liste de
clics : c'est l'habitude de vérifier d'où viennent les données, sur quelle
fenêtre on les regarde, et ce que l'écran ne montre pas.
