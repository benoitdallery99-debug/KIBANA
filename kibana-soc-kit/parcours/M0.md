# M0 — Prise en main

Avant de chercher, il faut savoir où l'on cherche. Ce module ne vous apprend
pas à enquêter : il vous donne les trois repères sans lesquels toute enquête
part de travers — **où** sont les données, **sur quelle période** vous les
regardez, et **de quel type** sont les champs que vous allez interroger.

## Les trois couches, en une phrase

Elasticsearch **stocke** les documents dans des index. Les journaux arrivent
dans des **data streams** : une suite d'index qui se relaient, pour qu'un
journal qui coule en continu n'ait pas à tenir dans un seul fichier. Kibana,
lui, n'interroge jamais un index directement : il passe par une **data view**,
qui désigne un motif d'index et un champ temporel.

Dans ce lab, la data view du parcours couvre les six sources de
l'organisation, et son champ temporel est `@timestamp`.

## Le type d'un champ décide de ce que vous pourrez en faire

Le type est fixé à l'indexation, pas à la recherche. Il ne se devine pas : il
se lit, dans la barre latérale de Discover.

| Type | Ce que c'est | Ce qu'il permet |
|---|---|---|
| `keyword` | une valeur exacte, non découpée | l'égalité stricte, le décompte |
| `text` | du texte découpé et analysé | la recherche de mots |
| `ip` | une adresse | la notation CIDR |
| `long` | un entier | les comparaisons |
| `date` | un instant | les plages de temps |

Cette table paraît théorique. Elle ne l'est pas : au module suivant, deux
requêtes qui se ressemblent donneront des résultats opposés, uniquement à
cause de cette colonne.

## Un écran vide n'est pas une absence de données

C'est le premier réflexe à acquérir, et celui qui fait perdre le plus de temps
quand il manque. Devant un Discover vide, vérifiez dans cet ordre :

1. la **data view** active — regardez-vous seulement la bonne source ?
2. la **plage de temps** — Kibana ouvre sur une fenêtre très courte ;
3. le **langage de requête** — KQL et Lucene ne s'écrivent pas pareil.

Le module M1 vous fera rencontrer le troisième point de la manière la plus
désagréable qui soit.
